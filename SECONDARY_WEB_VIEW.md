# Secondary web view

The main app uses `cordova.secondaryWebView`. It replaces the removed Android `CordovaActivity`/`IndependentWebViewHost` clone API and the removed iOS `CDVViewController` web-view-clone API and game-host bridge. It exposes `getCapabilities()`, `create(config)`, `destroy()`, `setTouchRegions({mode, rects})`, `send(envelope)`, `post(name, payload)`, `request(name, payload)`, `onEvent(listener)`, and `getMetrics()`. Calls return promises. `create` resolves to `{sessionId, storageIsolation}` and rejects with `{code, message}`. Create again only after `destroy`.

## Configuration

`url` is required and names a local bundle-relative path, `file:///android_asset/...`, or a filesystem `file://` document. Optional keys: `zOrder` (`below` default, or `above`), `opaque` (`false`), `backgroundColor` (`transparent`), `frame` (`fill` or CSS-pixel `{x,y,width,height}`), `hardwareAccelerated` (`true`), `processIsolation` (`shared` default, or `isolated`), `storageIsolation` (`origin` default, or `ephemeral`), `allowedRoots` (default: containing directory, entries `{path,kind:'bundle'|'file'}`), `maxParallelAssetReads` (unbounded or positive integer), `processWideMaxParallelAssetReads` (unbounded or positive integer), `assetReadTimeoutMs` (accepted for configuration compatibility; permit saturation now fails immediately with HTTP 503), `assetReadWatchdogMs` (`60000`, range `1000`–`300000`; expiry fails the in-progress asset response), `assetCacheMaxAgeSeconds` (`3600`, range `0`–`31536000`), `followSymlinks` (`false`), `heartbeatMs` (`2000`, `0` disables), `telemetry` (`{counters:true,perRequest:false,assetErrors:false}`), and `protocolVersions` (all supported). Colors use `transparent`, `#RRGGBB`, or `#RRGGBBAA`; `opaque:true` requires an opaque color. Invalid or unsupported modes return a typed error. The process-wide read limit applies only to secondary asset reads while a secondary instance requests it; main Cordova WebView assets remain unlimited by secondary sessions.

The content URL is `https://<root-derived-id>.secondary.local/r/<rootIndex>/<relativePath>`. Bundle roots map to `/android_asset/`; file roots use absolute filesystem paths. The host is stable for the same canonical entry root, distinct from the main view, and reused across sessions so `localStorage` and IndexedDB can persist without creating a new origin on every create. This is **origin isolation**, not ephemeral storage: data may remain on disk after destroy. In shared mode, WebView cookies remain in the app's cookie store; domain cookies can span sibling secondary hosts. In isolated mode, the dedicated process uses its own WebView data directory suffix, separating WebView storage from the host process as well as using the distinct origin. Neither mode wipes that storage on destroy. Android's `WebStorage.deleteOrigin()` is documented to clear Web SQL data, without a guarantee for `localStorage` or IndexedDB. Complete origin-scoped deletion has not been verified across API 24+. Android accepts both `origin` and `ephemeral` as configuration values for cross-platform compatibility, but **achieves and returns `origin` for either request**. `getCapabilities()` also reports `storageIsolation:'origin'`. `none` is unsupported because the secondary always has a distinct origin. iOS accepts the same values and can actually achieve `ephemeral`.

## Process mode

`shared` keeps the secondary WebView and all asset reads in the host application process. `isolated` binds `SecondaryWebViewService` in `:secondarywebview`; asset interception, canonical path checks, symlink policy, read limits, channels, and metrics run there. The template manifest declares this non-exported service and its `SecondaryWebViewProcessInit` provider for every application built on this fork, even if the app never requests isolated mode. The provider installs the WebView data directory suffix before the service or any WebView starts in that process. `destroy()` queues service teardown, then waits for the dedicated process to exit before completing and unbinding; the dedicated process then exits. Secondary process death emits `terminated`. Large channel payloads travel via file descriptors with the same 1 MiB limit as shared mode.

Surface embedding uses `SurfaceControlViewHost` (available from API 30) and a host `SurfaceView`. Supported isolated mode requires API 33 or newer, hardware acceleration, a reachable declared service, and the window touchable-region API introduced in API 33. `getCapabilities().processIsolation` probes the service and reports `true` only when these conditions hold; on API 30–32 and below API 30 it reports `false`. The API 33 requirement preserves host-controlled touch rectangles without Binder work per touch. In isolated mode, only `zOrder:'below'` is supported; `above` returns `UNSUPPORTED_MODE` because a surface above the host window cannot also preserve the host's touch-region routing. The main WebView page and any views covering the secondary must make the intended area transparent for a below surface to be visible. A region change cancels the secondary's active gesture before updating the host window's touchable region.

**Temporary performance-only escape hatch:** On API 30–32, `create({processIsolation:'isolated', unsafeAllowIsolatedBelowApi33:true})` starts the isolated process even though `getCapabilities().processIsolation` remains `false`. This flag defaults to `false` and has no effect on API 33+. It is unsupported and unsafe for product use. The host places the embedded `SurfaceView` **above** its window solely in this degraded state so content can receive all touches within its frame. `setTouchRegions` succeeds but has no effect, including for `none`, `all`, and `rects`; the secondary receives every touch in its frame. Create logs the unsafe mode and both touch limitations at `WARN` once. This path does not measure below-window visual composition or correct touch routing. Below API 30, the flag cannot start isolated mode.

### Composition checks

On an API 36 Pixel 9 emulator, an opaque isolated page with a distinct heading and red background rendered through a main WebView whose page background and body were set transparent at runtime. The host activity's blue app bar remained above the secondary content. This exercised `zOrder:'below'` with an opaque secondary and a transparent host content area. On an API 31 Android 12 emulator, the experimental path rendered an existing bundled page in the surface above the host; with touch mode `none`, an injected touchscreen tap followed that page's “Next page” link. This verifies the intended interactive degradation on that emulator. Translucent secondary content, arbitrary frame sizes, actual per-rectangle gestures in shipping mode, other devices, and API 30/32 were not visually exercised.

`getMetrics()` retrieves counters from the secondary process. `processStartToReadyNs` measures host create start through the secondary process being ready to call `loadUrl`; it is zero in shared mode. `createToFirstPaintNs` includes that startup cost, so compare the separate counter when evaluating first-create latency. `createToReadyNs` includes process startup as well.

In shared mode, WebView debugging is a process-wide setting, so the secondary follows the main WebView in `chrome://inspect`. For isolated mode, the host passes Cordova’s resolved `InspectableWebview` preference (or the app’s `FLAG_DEBUGGABLE` default) to the dedicated service. The service enables WebView debugging before constructing its WebView only when the main process enabled it. Asset-failure logs for denied, missing, timed-out, and watchdog-expired reads include the requested path relative to its declared root.

The secondary has no Cordova plugin bridge. Its sole global is `window.secondaryWebView`, with `request(name,payload)`, `post(name,payload)`, `subscribe(streamName,{rateHz,coalesce})`, `unsubscribe(id)`, `on(name,fn)`, and `onMessage`. The host decides how to answer requests; it can send a `res` envelope with the same `id`. ArrayBuffer payloads use WebViewCompat binary web messages when the feature checks pass; otherwise they use JSON with Base64 data.

The envelope is `{v,id,kind:'req'|'res'|'evt',name,payload,err?}`. Version 1 is supported. Each native event includes `sessionId` and `type`. Events: `ready`, `firstPaint`, `loadFailed`, `assetError`, `terminated`, `unresponsive`, `responsive`, `destroyed`, `memoryPressure`, `message`, `channelError`. `streams` is a secondary-facing event with one payload map of subscription IDs to `{streamName,data}` per display frame. The hard subscription rate cap is 60 Hz.

Native producers call `SecondaryWebViewStreams.push(streamName, sample)` from any thread and use `SecondaryWebViewStreams.hasSubscriber(streamName)` to stop sensors when nobody listens. Neither call needs an activity or manager instance. A push without a secondary or subscriber is a cheap no-op. Samples must be JSON values: `String`, finite `Number`, `Boolean`, `null`, `List`/`JSONArray`, and `Map`/`JSONObject` with string keys. Java arrays, including `float[]`, are not accepted. Invalid values, including non-finite numbers anywhere in the value, are dropped and emit host `channelError` with `INVALID_JSON` while subscribed. The older `SecondaryWebViewManager.pushSample` remains for compatibility and delivers only to that manager; new producers should use the public class API. Secondary pages use `subscribe(name,{rateHz:1..60,coalesce:'latest'|'batch'})`; `latest` keeps the newest sample, while `batch` retains samples in order. Delivery emits at most one `streams` event per display frame with a 60 Hz hard cap. In isolated mode the service mirrors subscribed stream names to the host, which batches producer samples once per host display frame and forwards the batch through a oneway Binder pipe; the service applies each subscription's coalescing and rate cap. Backgrounding, renderer termination, service death, and destruction clear subscriber state. `SecondaryWebViewIsolatedTest.nativeStreamsSharedAndIsolated` covers background-thread delivery, coalescing, rate limiting, invalid samples, mirrored subscriber state, background clearing, and destroy.

Touch mode defaults to `none`; only the main view can set `rects` or `all`. A region update cancels active gestures. Each pointer is routed independently according to where it first touches; later movement stays with that pointer's target until it lifts. Asset responses use `Cache-Control: private, max-age=<assetCacheMaxAgeSeconds>`; set the age to `31536000` for immutable content. Missing, denied (including outside a root or a blocked symlink), permit-saturated, and watchdog-expired reads return HTTP 404, 403, 503, and 504 responses with a short `text/plain` body and `Cache-Control: no-store`. They complete as responses for `fetch`, synchronous XHR, and asynchronous XHR. Only a failed entry document emits `loadFailed`; subresource failures do not destroy, reload, or retry the session. The interceptor tries permits without waiting on a WebView request thread, returning HTTP 503 immediately when saturated. No asset read or permit acquisition runs on either process main thread. A request racing session destruction may return 410 Gone; an unexpected read or interceptor error returns 500 Internal Server Error. Text, JavaScript, JSON, and SVG responses declare `charset=utf-8`. Byte-range (`Range`) requests are not implemented, so media seeking should not rely on this origin. The interceptor completes a read before sending HTTP 200 so a read timeout can still return 504. Assets at most 1 MiB are buffered in memory; larger assets spool to a temporary file and stream through a pipe, which uses bounded heap memory. A canceled, stalled, or renderer-abandoned read releases its permit; the watchdog closes reads held beyond the configured bound. Backgrounding clears subscriptions and pauses heartbeat monitoring; foregrounding resumes monitoring. Low-memory trim frees secondary WebView resources and emits `memoryPressure`. Renderer death emits `terminated` without reloading; the host decides when to destroy and recreate. Destroy removes handlers, views, subscriptions, and timers.

Set `telemetry.assetErrors:true` to receive host `assetError` events. Each event uses the standard envelope `{sessionId,type:"assetError",detail}`, where `detail` is `{sessionId,path,rootIndex,status,reason}`; `path` is relative to the requested root and `rootIndex` is -1 when the URL has no valid root number. Identical `(rootIndex,path,status,reason)` failures are emitted once per one-second window, with at most ten distinct events per window; suppressed events still increment the existing counters. The fork applies no policy on these failures. Hosts can use `assetError`, heartbeat, `unresponsive`, and `terminated` to decide whether to retry, reload, or destroy. The sample app's `assets/www/secondary-http-status-host.html` creates the secondary with this opt-in and checks `assetError` emission and the absence of `loadFailed` for subresources. Its secondary `assets/www/secondary-http-status.html` checks existing (200), missing (404), and denied (403) requests through `fetch`, synchronous XHR, and asynchronous XHR. Add `?mode=isolated` to the host URL to run it through the service process (API 30–32 uses the explicitly unsafe measurement flag).

## Threading and concurrency test

In shared mode, Cordova plugin calls and WebView changes run on the host main thread. In isolated mode, host plugin calls start on the host main thread, outbound Binder calls run on the controller's I/O executor, and value-returning service calls wait up to 30 seconds for work posted to the secondary process main thread. Service methods that return nothing post their work to that main thread and return immediately. **Value-returning main-thread work must never synchronously call back into the host.** `ISecondaryWebViewCallback` is one-way, and the service queues event serialization and Binder delivery on a dedicated event executor. The host's `onEvent` AIDL stub runs on a Binder pool thread, queues pipe reading on the controller I/O executor, and delivers the parsed event to the host main thread. In shared mode, `Listener.onEvent` runs on the host main thread; in isolated mode, the manager calls `Listener.onEvent` on the secondary main thread, which only queues delivery. Host JavaScript `onEvent` listeners run on the main WebView renderer thread after Cordova delivers the callback. Both WebViews invoke `shouldInterceptRequest` on WebView request threads, where path checks and bounded file reads run; permit acquisition is nonblocking. Asset error events are posted to the owning process main thread before delivery. The read watchdog runs on a scheduled executor; closing abandoned streams runs on a background pool. No Binder callback or `WKURLSchemeTask` equivalent is made while holding the asset stream lock.

`assets/www/secondary-concurrency-host.html?mode=shared` and `?mode=isolated` run three create/destroy cycles, with 240 image, asynchronous XHR, and fetch requests per phase, random aborts and image removals, navigation during the first phase, synchronous XHR status checks for 200/404/403, and destruction during outstanding requests. The page probes the host main thread through `pingMainThread` and the secondary main thread through `getMetrics` every 100 ms; any callback or timer gap above one second fails the run. `SecondaryWebViewIsolatedTest.concurrencyStressSharedAndIsolated` drives both modes and fails if the host main thread itself cannot answer a one-second probe. On API 30–32 the isolated run uses `unsafeAllowIsolatedBelowApi33` only for measurement; API 33+ exercises the supported path.

The concurrency instrumentation passed on an API 30 emulator (shared plus the experimental isolated path) and an API 36 emulator (shared plus the supported isolated path). The HTTP 200/404/403 synchronous XHR assertions are part of each run. These runs did not measure visual composition or touch behavior.

Channel validation uses three distinct codes in both directions. `INVALID_JSON` means an envelope contains a non-finite number (`NaN`, `Infinity`, or `-Infinity`) or another value that cannot be represented as JSON, including one nested in an array or object. `MESSAGE_TOO_LARGE` means valid JSON exceeds the 1 MiB UTF-8 channel limit. `INVALID_MESSAGE` means malformed JSON or wire data, a malformed envelope or packet (including a short binary packet or null bridge string), or an application attempt to use the reserved `__secondaryChannelError` message name. Explicit top-level `undefined` payloads become `null`; nested `undefined` is `INVALID_JSON`. Host `send`, `post`, and `request` reject with `{code,message}`. Secondary-page `request` rejects with the same code and reports host `channelError`. Secondary-page `post` remains fire-and-forget and returns `undefined`; failures emit host `channelError` and `console.warn` in the page, without an unhandled rejection. Internal posts also swallow transport rejection during teardown or backgrounding. Validation failures do not end the session. The sample `secondary-channel-validation-host.html` and its secondary page exercise both directions in shared and isolated modes, the size boundary, malformed input, reserved name, undefined payloads, and a subsequent successful message.

## Pipe and callback threading

Binder callbacks carrying events are `oneway`. The isolated service posts void commands to its main thread; value-returning Binder calls may wait for it, but must never synchronously call the host. The host reads event payloads on a dedicated event executor and metric payloads on separate metric workers. Each payload pipe owns a daemon writer thread; receiving has a five-second deadline and a 1 MiB size cap. JSON nesting deeper than 64 levels is rejected before parsing. Asset reads and permits run on WebView request threads; permits fail immediately when saturated. `shouldInterceptRequest` catches unexpected runtime and allocation errors and returns HTTP 500 when possible. An isolated-service crash emits `terminated` and is not automatically restarted. `telemetry.perRequest` retains at most 256 traces per session.

The instrumentation stress fixture covers shared and isolated mode on API 30 and API 33+, with 240 requests per phase, synchronous XHR status checks, malformed channel types, a 600 KiB event while metrics are polled, navigation, cancellation, destroy during active requests, and repeated create/destroy. A separate test destroys during create and checks callback order. Another generates a 2 MiB file and verifies it arrives intact through the large-asset pipe.
